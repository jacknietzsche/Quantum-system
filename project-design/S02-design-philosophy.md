# S2 — 设计理念与参考框架

## 2.1 核心设计哲学

**"像专业投资机构一样思考，像个人投资者一样执行"**

| 理念 | 来源 | 在本系统中的体现 |
|------|------|------------------|
| 多智能体协作 | TradingAgents | 12个专业Agent分工协作 |
| 对抗性辩论 | TradingAgents-AShare | 多轮多空辩论+三方风险辩论 |
| 投资大师思维 | AI Hedge Fund | 可选的大师视角增强层 |
| 超级Agent框架 | DeerFlow 2.0 | 子Agent调度、上下文工程、长期记忆 |
| 渐进式技能加载 | DeerFlow 2.0 | Skill按需加载，保持上下文精简 |
| 结构化输出 | TradingAgents | Pydantic schema确保输出可解析 |
| 决策反思闭环 | TradingAgents | 历史决策记忆+反思注入 |
| Agent可观测性 | AgentOps | LLM成本追踪、决策审计、会话回放 |

## 2.2 设计约束（硬性）

| 约束 | 为什么 | 违反后果 |
|------|--------|----------|
| 纯API调用 | 个人电脑算力有限，本地大模型推理慢且效果差 | 需要GPU，成本高，维护难 |
| 免费数据源 | 零成本运行是核心卖点，个人用户不应有持续支出 | 月费几百到几千，难以持续 |
| 个人使用 | 不需要多用户/权限/租户隔离，简化架构 | 过度设计，开发周期翻倍 |
| A股专注 | A股规则特殊（T+1/涨跌停/手数限制），通用方案不适用 | 规则错误导致交易失败 |
| 可执行输出 | 用户要的是能直接下单的交易计划，不是需要二次加工的分析报告 | 输出无法直接使用，用户还得自己决策 |
| 零基础设施 | 不需要运维Docker/Redis/MongoDB，一键启动即用 | 增加部署和维护成本 |

## 2.3 决策优先级

当设计冲突时，按以下顺序取舍：

| 优先级 | 原则 | 举例 |
|--------|------|------|
| 1 | 安全性 | 不亏钱 > 赚钱。宁可错过机会，不可冒不可控的风险 |
| 2 | 可执行性 | 输出可直接用 > 输出仅供参考。交易计划必须包含具体数字 |
| 3 | 成本 | 免费 > 付费。能用免费方案解决的不花钱 |
| 4 | 简单性 | 少代码 > 多代码。能100行解决的不写500行 |
| 5 | 性能 | 够用 > 最优。3分钟内完成分析即可，不需要30秒 |

## 2.4 反模式（禁止事项）

| 反模式 | 原因 | 替代方案 |
|--------|------|----------|
| 引入付费API | 违反零成本约束 | 用AKShare/BaoStock等免费源 |
| 本地部署大模型 | 违反纯API约束 | 用DeepSeek API（deepseek-chat免费500万token/天） |
| 复杂微服务架构 | 个人项目不需要服务发现/负载均衡 | 单体应用+SQLite |
| 通用型设计 | A股规则（T+1/涨跌停）全球独一无二 | A股特化 |
| 纯自然语言输出 | 无法直接执行，需要人工解读 | Pydantic结构化输出 |
| Agent间直接共享状态 | 耦合过紧，难以调试和扩展 | 通过state字典传递结果 |
| 单Agent包办所有 | 上下文溢出，决策质量差 | 12个专职Agent分工 |
| 忽略失败降级 | 一个Agent挂了全部停摆 | 每个Agent有default_factory |

## 2.5 成功标准

| 指标 | 目标 | 测量方式 |
|------|------|----------|
| 分析完整度 | 12个Agent全部执行 | 日志检查 |
| 单股分析时间 | <3分钟 | 计时 |
| 每日token消耗 | <50万token | token计数器 |
| 交易计划可用率 | >80%可直接执行 | 人工抽检10份计划 |
| 决策可追溯率 | 100% | 每个决策记录参与Agent |
| 回测胜率 | >55%（跑赢沪深300） | 月度回测 |

## 2.6 可操作的设计原则

| 原则 | 具体要求 | 反例 |
|------|----------|------|
| 单一职责 | 每个Agent只做一件事（市场分析师不分析基本面） | 一个Agent包办所有分析 |
| 松耦合 | Agent间通过state字典传递结果，不直接调用对方 | 直接修改对方的变量 |
| 容错优先 | 单个Agent失败用默认值，不阻断整个流程 | 一个Agent超时全部停摆 |
| 结构化输出 | 所有决策Agent使用Pydantic schema | 自然语言文本无法解析 |
| 可追溯 | 记录每个决策由哪些Agent参与、辩论了什么 | 决策无法复盘 |
| 渐进加载 | Skill按需加载，不一次注入所有上下文 | 一次加载所有Skill占用token |

## 2.7 核心模式总结

本系统采用了8个成熟开源项目的设计模式（详见S04）：

| 模式 | 来源 | 解决什么问题 |
|------|------|-------------|
| Agent工厂模式 | TradingAgents | LLM延迟绑定，同一Agent可用不同模型 |
| 信号架构 | AI Hedge Fund | 统一输出格式，下游可解析 |
| 错误分层 | Swarms | LLM失败/工具失败/记忆失败分层处理 |
| 通信流控制 | Agency Swarm | 显式定义Agent间通信方向 |
| 状态机模式 | MetaGPT | 不同Agent用不同执行模式 |
| 上下文压缩 | Swarms | 辩论多轮后自动压缩历史 |
| 记忆分层 | MetaGPT+TradingAgents | 长期记忆+工作记忆+决策日志 |
| 确定性约束+LLM | AI Hedge Fund | 风险管理纯量化，组合经理在约束内决策 |

## 2.8 场景示例

### 场景：全市场扫描 → 明日交易计划

**用户需求**: "扫描A股全部标的，给出明天的交易计划"

**系统执行流程**:

```
Step 1: 市场感知
  → 获取上证/深证/创业板指数状态
  → 判断市场环境: 牛市/熊市/恐慌/过热/中性
  → 输出: 当前为"中性"市场，仓位上限60%

Step 2: 全市场初筛（快速过滤，不调用LLM）
  → 5000+只股票 → 硬性过滤（排除ST/停牌/次新/低流动性）
  → 剩余 ~800只进入候选池

Step 3: 多因子评分（纯量化，不调用LLM）
  → 价值因子: PE/PB/股息率
  → 成长因子: 营收增速/利润增速
  → 动量因子: 20日涨幅/RSI
  → 质量因子: ROE/现金流
  → 综合评分 → Top 50进入深度分析

Step 4: 深度分析（50只 × 12个Agent = 600次LLM调用）
  对每只Top 50股票执行完整分析流程:
  ┌─────────────────────────────────────────────┐
  │ 4个分析师并行 → 4份分析报告                  │
  │ ↓                                            │
  │ 多空辩论(2轮) → 投资计划                     │
  │ ↓                                            │
  │ 交易员 → 交易提案(入场价/止损/止盈/仓位)      │
  │ ↓                                            │
  │ 三方风险辩论(2轮) → 风险评估                  │
  │ ↓                                            │
  │ 组合经理 → 最终决策(Buy/Sell/Hold)            │
  └─────────────────────────────────────────────┘

Step 5: 组合优化
  → 从50只中选出Top 5-10只
  → 确保行业分散（不超过3只同一行业）
  → 确保仓位合规（单只不超过总资金15%）
  → 计算每个标的的具体仓位金额

Step 6: 输出明日交易计划
  ┌─────────────────────────────────────────────┐
  │ 日期: 2026-06-14 (周一)                       │
  │ 市场状态: 中性 | 仓位上限: 60%                │
  ├─────────────────────────────────────────────┤
  │ 买入计划:                                     │
  │ 1. 600519 贵州茅台  Buy @ 1500.00            │
  │    止损: 1425.00 | 止盈: 1650.00 | 仓位: 5% │
  │    论据: Q2营收超预期，直营占比提升...          │
  │                                               │
  │ 2. 000858 五粮液    Buy @ 135.00             │
  │    止损: 128.00 | 止盈: 155.00 | 仓位: 4%   │
  │    论据: 白酒板块轮动，估值修复...              │
  │                                               │
  │ 3. 601318 中国平安  Buy @ 52.00              │
  │    止损: 49.50 | 止盈: 58.00 | 仓位: 3%     │
  │    论据: 保险板块低估值，北向资金持续流入...    │
  ├─────────────────────────────────────────────┤
  │ 持有计划:                                     │
  │ 4. 002594 比亚迪    Hold                     │
  │    当前仓位: 8% | 盈利: +12.3%               │
  │    论据: 新能源趋势未变，继续持有              │
  ├─────────────────────────────────────────────┤
  │ 卖出计划:                                     │
  │ 5. 600036 招商银行  Sell @ 38.50             │
  │    当前仓位: 3% | 亏损: -5.2%                │
  │    论据: 银行板块承压，止损触发               │
  └─────────────────────────────────────────────┘

Step 7: 记录决策
  → 保存到decision_log（SQLite）
  → 标记为"pending"（等待结果验证）
  → 30天后自动反思（如果结果已知）
```

**Token消耗估算**:
- 初筛+评分: ~0 token（纯量化）
- 深度分析: 每只股票 ~17,500 token（4分析师+辩论+研究经理+交易员+风险辩论+组合经理）
- 组合优化: ~5,000 token
- **10只股票总计: ~180,000 token**（DeepSeek免费额度500万/天，完全覆盖）
- **50只股票总计: ~880,000 token**（超出40万日预算，需启用快速模式）

> **预算约束**: S03设定每日token预算上限40万。全市场扫描50只股票时，约在第20-22只触发"快速模式"（跳过辩论和大师层，仅执行分析师+交易员+组合经理），后续股票以简化流程完成分析。

**执行时间估算**:
- 初筛+评分: ~30秒（纯计算）
- 10只深度分析: ~10 × 30秒 = 5分钟（并行可压缩到3分钟）
- 50只深度分析: ~50 × 30秒 = 25分钟（并行可压缩到10分钟，快速模式更快）
- 组合优化: ~10秒
- **总计: ~5-25分钟**（取决于分析数量）
