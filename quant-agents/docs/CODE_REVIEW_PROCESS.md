## 1. 审查生命周期

```
┌─────────┐     ┌──────────┐     ┌──────────┐     ┌──────────┐     ┌─────────┐
│  提交PR  │────▶│ 自动检查  │────▶│ 人工审查  │────▶│ 修改完善  │────▶│  合并   │
└─────────┘     └──────────┘     └──────────┘     └──────────┘     └─────────┘
                     │                │                ▲
                     ▼                ▼                │
               ┌──────────┐    ┌──────────┐           │
               │  CI失败   │    │ 请求修改  │───────────┘
               │ 自动驳回  │    └──────────┘
               └──────────┘
```

### 阶段说明

| 阶段 | 做什么 | 谁负责 | 时间预期 |
|------|--------|--------|----------|
| 1. 提交 PR | 填写模板，自检清单 | 作者 | — |
| 2. 自动检查 | Pre-commit Hooks + CI 运行 | 系统 | < 5 min |
| 3. 人工审查 | 按标准逐项检查代码 | 审查者 | < 24h |
| 4. 修改完善 | 根据反馈修改代码 | 作者 | < 48h |
| 5. 合并 | 审查通过后合并到主分支 | 审查者/维护者 | 即时 |

### 超时处理

- **审查超时**（> 24h）：作者可在 PR 中 @审查者 提醒
- **修改超时**（> 48h）：审查者可关闭 PR，作者后续重新提交
- **紧急修复**：标记 `hotfix` 标签，加速审查

## 2. 角色与职责

### 2.1 作者 (Author)

**职责**：
- 提交前完成 [PULL_REQUEST_TEMPLATE.md](../.github/PULL_REQUEST_TEMPLATE.md) 自检清单
- PR 描述清晰：做了什么、为什么做、如何测试
- PR 保持小范围：建议单个 PR < 500 行变更（不含测试）
- 对所有审查评论在24小时内响应
- 修改后重新请求审查（使用 GitHub "Re-request review" 功能）

**禁忌**：
- ❌ 在审查期间 force push 覆盖已审查的提交
- ❌ 忽略审查意见直接合并
- ❌ 一个 PR 包含不相关的多个变更

### 2.2 审查者 (Reviewer)

**职责**：
- 在 24 小时内开始审查（紧急修复 < 4 小时）
- 按 [CODE_REVIEW_STANDARDS.md](./CODE_REVIEW_STANDARDS.md) 逐项检查
- 区分严重等级：🔴 Blocker / 🟡 Suggestion / 💭 Nit
- 对不确定的项标注"问题"而非"必须改"
- 发现问题时建议具体修复方案

**素质要求**：
- 熟悉对应模块的业务逻辑
- 了解项目代码审查标准
- 保持建设性态度

### 2.3 维护者 (Maintainer)

**职责**：
- 最终审批和合并权限
- 解决审查者与作者之间的分歧
- 确保审查质量一致性
- 维护审查标准文档

## 3. 自动化门禁

### 3.1 Pre-commit Hooks（本地）

```bash
# 安装（仅需一次）
pip install pre-commit
pre-commit install

# 每次提交前自动运行
git commit -m "feat: add north-bound flow monitor"
# → ruff check → ruff format → isort → prettier → detect-secrets → ...

# 跳过 hooks（仅紧急情况，需在 PR 中说明理由）
git commit --no-verify -m "hotfix: broken API endpoint"
```

### 3.2 CI 流水线（GitHub Actions，建议配置）

```yaml
# .github/workflows/ci.yml
name: CI
on: [pull_request]

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pre-commit/action@v3.0.1

  test:
    needs: lint
    runs-on: ubuntu-latest
    strategy:
      matrix:
        project: [a-share-investment-system]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.10'
      - run: |
          cd ${{ matrix.project }}
          pip install -e ".[dev]"
          pytest --cov --cov-report=xml
      - uses: codecov/codecov-action@v5
```

### 3.3 自动检查清单

| 检查项 | 工具 | 触发时机 | 阻塞级别 |
|--------|------|----------|----------|
| Python Lint | ruff | pre-commit + CI | 🔴 阻塞 |
| Python 格式化 | ruff format | pre-commit + CI | 🔴 阻塞 |
| 导入排序 | isort | pre-commit + CI | 🔴 阻塞 |
| 类型检查 | mypy | CI | 🟡 告警 |
| 安全扫描 | bandit | CI | 🔴 阻塞 |
| 密钥检测 | detect-secrets | pre-commit | 🔴 阻塞 |
| 前端格式化 | prettier | pre-commit + CI | 🔴 阻塞 |
| 前端 Lint | eslint | CI | 🟡 告警 |
| 单元测试 | pytest | CI | 🔴 阻塞 |
| 覆盖率 | pytest-cov | CI | 🟡 告警 |

## 4. 审查步骤

### Step 1: 浏览全貌（2 分钟）

- 阅读 PR 标题和描述，理解变更意图
- 查看文件变更列表，确认范围合理
- 如果范围过大（> 500 行），请求拆分

### Step 2: 检查正确性（核心，占审查 50% 时间）

- 逻辑是否正确？边界情况是否处理？
- 是否有前视偏差？（量化专属 — 参见标准 7.1）
- 回测逻辑是否与实盘逻辑一致？
- 数据源降级链是否完整？

### Step 3: 检查安全（占审查 20% 时间）

- 是否有硬编码的密钥/Token？
- 外部输入是否经过验证？
- SQL/命令注入风险？
- 敏感信息是否泄露到日志？

### Step 4: 检查可维护性（占审查 20% 时间）

- 命名是否清晰自解释？
- 是否有过度的代码重复？
- 复杂逻辑有无注释？
- 公开 API 有无 docstring？

### Step 5: 检查测试（占审查 10% 时间）

- 关键路径是否有测试覆盖？
- 测试是否验证了正确的行为（而非实现细节）？
- 边界情况和错误路径是否测试？

### Step 6: 检查性能（占审查 10% 时间）

- 有无 N+1 查询？
- 大数据处理是否考虑分页/流式？
- 外部 API 调用有无超时和重试？

## 5. 评论规范

### 5.1 评论格式

```
[等级] [类别] 简短标题

具体说明：问题是什么、为什么是问题。

建议的修复方案（可选，但推荐提供）：

回复方式：
- 已修复：在对应位置 @审查者 确认
- 不修改：说明理由
- 有疑问：直接回复讨论
```

### 5.2 评论示例

```
🟡 **可维护性：重复代码应提取**

`data_fetcher.py:45-68` 和 `data_bus.py:120-143` 有几乎相同的行情解析逻辑。

**Why:** 两处修改需要同步，容易遗漏导致数据不一致。

**Suggestion:**
提取到 `utils/quote_parser.py` 作为 `parse_spot_quote(row) -> StockQuote`。
```

```
💭 **命名：变量名建议更精确**

`data_fetcher.py:87`: `r` → `row` 或 `quote_row`
变化幅度很小，但提升可读性。
```

### 5.3 评论禁忌

- ❌ **人身攻击**："这代码写得真烂"
- ❌ **命令式**："你必须改成XX"（除非是 Blocker 级别的安全问题）
- ❌ **含糊其辞**："这里有问题"（不说明什么问题）
- ❌ **评审过度**：对风格问题吹毛求疵（自动格式化工具已覆盖的不要提）

### 5.4 高效评论技巧

- **一次说清所有问题**：避免分多次评论造成往返
- **用"我们"而非"你"**："我们应该..."比"你应该..."更好
- **提问题而非下结论**：对于不确定的部分，先问"这里是否有XX考虑？"
- **指出好的部分**：看到好的设计、巧妙的实现要点赞："👍 这个降级链设计很清晰"

## 6. 常见场景处理

### 场景 1：审查者与作者意见不一致

1. 双方在 PR 评论中讨论（保持公开）
2. 若无法达成一致，@维护者介入
3. 维护者决策为最终决定，记录技术决策理由

### 场景 2：紧急修复 (Hotfix)

1. PR 标题标记 `[HOTFIX]`
2. 简化流程：只需 1 位审查者批准
3. 仍必须通过自动化检查
4. 事后补充完整测试

### 场景 3：大型重构

1. 先发设计文档或 RFC，获得预先共识
2. 拆分为多个小 PR（每个 PR < 500行）
3. 使用 Feature Flag 或分支策略隔离风险
4. 每个 PR 需独立可测试

### 场景 4：第三方依赖升级

1. 检查 CHANGELOG 中的 breaking changes
2. 在 PR 描述中说明升级理由
3. 完整运行测试套件
4. 在 staging 环境验证（如有）

### 场景 5：策略参数调整

量化项目特有的审查关注点：

1. **参数来源**：调整依据是什么？（历史回测？论文？经验？）
2. **稳健性**：参数小变动是否导致结果剧烈变化？
3. **过拟合风险**：回测集上的提升是否在验证集上复现？
4. **文档更新**：参数变更需同步更新策略文档

## 7. 审查度量

### 7.1 审查质量指标

| 指标 | 目标值 | 说明 |
|------|--------|------|
| 审查响应时间 | < 24h | PR 提交到首次审查 |
| 审查周期 | < 48h | 提交到最终合并 |
| Blocker 密度 | < 2 个/100行 | 减少低质量代码进入审查 |
| 回滚率 | < 5% | 合并后因严重问题回滚的比例 |

### 7.2 审查健康度检查

每月回顾：

- [ ] 是否有超过 72 小时未审查的 PR？
- [ ] 审查评论是否建设性和可操作？
- [ ] 是否有合并后发现严重 Bug 的情况？（需改进审查覆盖面）
- [ ] 自动化检查是否有效减少了人工审查负担？
