## 1. 定位与触发条件

Interrupt 节点是图中一种**特殊控制节点**，在 `execution_plan` 中标记为 `type: "confirm"`。

**作用**:
- 暂停自动执行，将控制权交还用户
- 通过 SSE 通知前端展示确认界面
- 等待用户确认/取消/修改指令后继续

**触发时机**: 执行调度器按计划推进，当 `current_step_index` 指向一个 `type: "confirm"` 步骤时进入。

---

## 2. 涉及 State 字段

| 字段 | 作用 |
|------|------|
| `status` | 中断时设 `"waiting_user"`，恢复后改 `"executing"` |
| `interrupt_data` | 携带给前端渲染确认界面的信息 |
| `user_confirmation` | 恢复时由外部注入，包含用户决策 |

---

## 3. 进入等待状态流程

```
1. 执行调度器识别到 type=confirm_plan / confirm_email / wait_for_user 步骤（2026-06-07 补强 P0-1：枚举扩展为 5 个值）→ 调用 Interrupt 节点
2. Interrupt 节点填充 interrupt_data:
   - type: str ("confirm_plan" / "confirm_email" / "wait_for_user")
   - message: str (给用户的自然语言提示)
   - plan_summary: list[str] (可选，confirm_plan 时显示步骤摘要)
   - options: list[str] (["confirm", "cancel", "modify"])
3. Interrupt 节点更新 State:
   - status = "waiting_user"
   - interrupt_data = {...}
   - messages 追加 system 消息："系统提示：已向用户请求确认（类型：{type}）。等待用户操作…"（2026-06-07 补强 P0-4 / F-5）
4. Interrupt 节点调用 LangGraph 的 interrupt()，暂停图执行
   → checkpoint 保存当前 State
   → 异常由工作流引擎捕获，非错误，正常流程
5. SSE 推送 waiting_confirmation 事件给前端
6. 前端展示确认模式 UI
```

---

## 4. 恢复执行流程

用户操作 → 前端调用 `POST /api/task/{run_id}/confirm`:

```json
{
  "action": "confirm",    // confirm | cancel | modify
  "params": {}            // modify 时携带修改参数
}
```

后端处理:
```
1. 根据 run_id 找到暂停的 LangGraph 图实例 (checkpoint)
2. 将 user_confirmation 写入 State
3. 更新 status = "executing"
4. 通过 LangGraph 恢复机制继续图执行
5. Interrupt 节点读取 user_confirmation:
   - "confirm" → 正常完成，继续下一步
   - "cancel" → 标记 status = "cancelled" 并清理
   - "modify" → 更新 config/plan，重新执行 (初始可暂不支持)
```

**关键**: 恢复时 LangGraph 从 checkpoint 加载 State，`user_confirmation` 必须通过 `config.configurable` 或 `Command(resume=...)` 传入。

---

## 5. 超时处理

用户可能长时间不响应。

**方案**:
- Interrupt 暂停后启动后台计时器 (30 分钟)
- 超时后自动注入 `user_confirmation = {action: "timeout"}`
- Interrupt 节点识别 timeout → 标记 `cancelled`
- SSE 推送"任务已超时取消"
- 服务重启后扫描 `status == "waiting_user"` 的任务，自动取消

## 6. SSE 事件定义

**中断通知**:
```json
{
  "event": "waiting_confirmation",
  "data": {
    "type": "confirm_plan",
    "message": "已生成今日分析计划...",
    "plan_summary": ["1. 检查数据", "2. 市场分析", "3. 选股", "4. 深度分析", "5. 报告"],
    "options": ["confirm", "cancel"],
    "params": {                    // 2026-06-07 补强 P0-1 / F-6：confirm 类型时携带上下文 payload
      "max_candidates": 10,
      "style": "neutral"
    }
  }
}
```

**`params` 字段语义（F-6）**：因 `type` 枚举已区分 `confirm_plan` / `confirm_email` / `wait_for_user`，`params` 直接存放该确认类型所需的上下文参数（如 `confirm_plan` 含 `plan_summary` / `max_candidates` / `style`；`confirm_email` 含 `to / subject / preview_html`）。`PlanStep.params` 字段**不为 null**，由 `plan_generator` 生成计划时填充。

**恢复后**：SSE 继续推送后续节点进度事件，无缝衔接。

---

## 7. 边界情况

| 场景 | 处理 |
|------|------|
| 恢复时任务已终态 | 返回 400: "任务已结束，无法确认" |
| 重复确认 | 幂等处理，第二次返回"已确认" |
| 前置步骤失败 | 不应进入中断，计划中 confirm 步骤的 depends_on 必须全部 success |
| Interrupt 节点自身异常 | 视为系统错误，几乎不会发生（纯状态操作） |

## 8. LangGraph 集成原理

```
Interrupt 节点函数:
  1. 填充 interrupt_data + 更新 status
  2. 调用 result = interrupt(interrupt_data)  # 暂停点
  3. 读取 result → 这是恢复时注入的 user_confirmation
  4. 根据 action 决定下一步

恢复调用:
  graph.ainvoke(Command(resume=user_confirmation), config)
  → interrupt() 返回 user_confirmation
  → 节点继续执行
```

#### §8.1 interrupt() 恢复语义说明

**核心结论**：`interrupt()` 是**恢复点**（resume point），**不是重入点**（re-entry point）。

**LangGraph 原生行为**：
- 节点函数体内调用 `interrupt(interrupt_data)` 时，LangGraph **冻结**该节点函数栈、序列化 State 到 checkpoint、暂停图执行。
- 外部调用 `graph.ainvoke(Command(resume=user_confirmation), config)` 时，LangGraph 从 checkpoint **恢复 State**、**从 `interrupt()` 调用处继续**——**节点函数体内 `interrupt()` 之前的代码不重跑**。

**State 字段"已消费标记"（Layer 2 幂等保障）**：
```python
# interrupt_node 函数体内
from langgraph.types import interrupt, Command
from datetime import datetime

def interrupt_node(state: dict) -> dict:
    # 检查是否已恢复过（防御性，正常不会发生）
    if state.get("interrupt_consumed"):
        return {"interrupt_consumed": True}  # 幂等返回

    step = state["execution_plan"][state["current_step_index"]]

    # 1. 构造 interrupt_data（2026-06-07 补强 P0-1：type 直接是 step.type）
    interrupt_data = {
        "type": step["type"],            # confirm_plan / confirm_email / wait_for_user
        "message": step.get("description", "请确认是否继续"),
        "plan_summary": _format_plan_summary(state["execution_plan"]),
        "options": ["confirm", "cancel", "modify"],
        "params": step.get("params", {}),  # 确认类型所需上下文
    }

    # 1.1 追加 system 消息（2026-06-07 补强 P0-4 / F-5）
    system_msg = {
        "role": "system",
        "content": f"系统提示：已向用户请求确认（类型：{step['type']}）。等待用户操作…",
        "timestamp": datetime.now().isoformat(),
    }

    # 2. 推送 SSE
    _emit_sse(state["run_id"], "waiting_confirmation", interrupt_data)

    # 3. 调用 interrupt() 暂停
    user_confirmation = interrupt(interrupt_data)

    # 3.1 追加用户操作的 system 消息（2026-06-07 补强 C-5）
    user_action_msg = {
        "role": "system",
        "content": f"用户已执行：{user_confirmation.get('action', 'cancel')}",
        "timestamp": datetime.now().isoformat(),
    }

    # 4. 恢复后执行（不会重入第 1-3 步）
    return {
        "user_confirmation": user_confirmation,
        "status": "executing",
        "interrupt_consumed": True,  # 写入者：interrupt_node 自身
        "messages": state.get("messages", []) + [system_msg, user_action_msg],
    }
```

**配合 M3.5 §1.2 State 新增字段**：
- `interrupt_consumed: bool`（默认值 `False`）
- 写入者：`interrupt_node` 函数（恢复时设为 `True`）
- 读取者：`interrupt_node` 函数（检查幂等）
- 不持久化到 LangGraph checkpoint 之外的业务表

**防御性场景**：
- 同一 `run_id` 重复调用 `POST /api/tasks/{run_id}/confirm` → LangGraph 第二次进入 `interrupt_node`，`interrupt_consumed=True` 已存在 → 直接 return，不重复推送 SSE
- 配合 M2 §4 `idempotency_key` 机制双层保护（详见 M2 文档）

→ 由 software-product-manager 于 2026-06-07 补强，依据 review 第 2 轮 P0。

## 9. 状态转换图

```
[planning] → (生成计划) → [executing]
                               │
                         推进步骤时遇到 confirm
                               │
                         status = "waiting_user"
                         SSE 推送中断事件
                         启动 30min 计时器
                               │
                  ┌────────────┼────────────┐
                  │            │            │
               confirm      cancel      timeout (30m)
                  │            │            │
           [executing]  [cancelling]  [cancelling]
             继续下一步       │            │
                              │ 清理资源    │ 清理资源
                              ↓            ↓
                          [cancelled]  [cancelled]
```

**取消流程的中间态（`cancelling` → `cancelled`）**：

- 用户在 SSE 流关闭时点击"停止"按钮 → 前端调用 `POST /api/tasks/{run_id}/cancel` → 后端将 `status` 设为 `cancelling`。
- 后台清理协程（关闭 LLM 连接、释放文件句柄、写 partial result 到 `agent_runs` 表）→ 完成后 `status` 设为 `cancelled`。
- **前端**根据 `cancelling` 状态显示"正在停止…"提示，**避免**直接跳到 `cancelled` 造成 UI 闪烁。
- 30 分钟超时同理：`waiting_user` 状态下计时器到期 → `cancelling` → 清理 → `cancelled`。

→ 由 software-product-manager 于 2026-06-07 补强，依据 review 第 2 轮 P1。
