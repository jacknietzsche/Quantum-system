# Module 3.5: Agent 执行运行时 — State 设计

**前置**: 模块3 (Agent 架构) 已定  
**用途**: 为 LangGraph 图、Master Agent 调度器、前端 SSE 交互提供统一数据契约  
**核心原则**: State 是"已经发生的和正在发生的"，不是"将要发生的"。所有节点只追加或更新已知事实。  
**状态**: Draft | **日期**: 2026-06-07

> ⚠️ **TARGET ARCHITECTURE** — 本文档描述目标架构，非当前实现。当前实际架构参见 `docs/ACTUAL_ARCHITECTURE.md`。

## 1. State 总览

State 是一个 **扁平字典**（嵌套结构会增加节点耦合），按功能域分为 5 组。

### 1.1 会话与用户交互

| 字段 | 类型 | 写入者 | 读取者 | 说明 |
|------|------|--------|--------|------|
| `messages` | list[Message] | Master Agent (汇总时), 用户消息注入, **Interrupt 节点（暂停/恢复时追加 system 消息，2026-06-07 补强 P0-4/F-5）** | Master Agent (上下文), 前端 (展示) | 对话历史，每条消息有 role (user/assistant/system) 和 content |
| `user_intent` | str | Master Agent (意图解析) | 条件路由节点, **`plan_generator` 查 skill_registry 过滤工具（C-3）** | 枚举: `daily_analysis`, `stock_deep_dive`, `reflection`, `general_chat` |
| `user_confirmation` | dict | Interrupt 节点恢复时注入 | 后续节点 | `{action: "confirm"/"cancel"/"modify", params: {...}}` |

### 1.2 任务与计划

| 字段 | 类型 | 写入者 | 读取者 | 说明 |
|------|------|--------|--------|------|
| `run_id` | str | **API 层（/api/chat）在创建任务时生成（2026-06-07 补强 C-10）**，注入 init 节点 State | 全部节点（日志关联） | 唯一标识，贯穿全程 |
| `execution_plan` | list[Step] | Master Agent (计划生成) | 执行调度器, Interrupt 节点 | 有序步骤列表；**`type` 字段枚举：`skill / agent / confirm_plan / confirm_email / wait_for_user`（2026-06-07 补强 P0-1）** |
| `current_step_index` | int | 执行调度器 | 执行调度器, 条件路由 | 当前执行到第几步，初始 -1 |
| `step_results` | dict[str, Any] | 各执行节点 | 汇总节点, 后续步骤 | key = step_id，value = 该步骤输出。`analysis_results` 是 `step_results[analyst_step_id]` 的子集/快捷访问，实际数据只存一份。 |
| `status` | str | 执行调度器, Interrupt 节点 | 全部节点, 前端 | **终态枚举**：`completed \| failed \| cancelled`（2026-06-07 补强 F-8）；中间态：`planning → executing → waiting_user → cancelling`；超时统一归为 `cancelled`，`status_reason` 字段记录原因 |
| `errors` | list[ErrorEntry] | 各节点（捕获异常时追加） | 汇总节点, 前端 | 非致命错误收集，致命错误直接标记 status=failed |
| `node_count` | int | 每个节点递增（**2026-06-07 补强 C-4**：硬限 200） | error_handler, 前端 | 防止 execution_loop 死循环 |

**Step 结构**（`execution_plan` 的元素，**2026-06-07 更新 P0-1**）:
- `step_id`: 唯一标识，如 `"step_1"`
- `type`: `"skill"` | `"agent"` | `"confirm_plan"` | `"confirm_email"` | `"wait_for_user"`（5 个值）
- `target`: Skill 名或 Agent 名（agent 类型时不可为 "master"）
- `params`: 输入参数（可引用前面步骤的结果，用 `"$step_id.field"` 占位符）；**`confirm_*` 类型时 params 是该确认用的 payload**（如 `confirm_email` 含 `to/subject/preview`）
- `depends_on`: list[step_id] 前置依赖
- `description`: 给用户看的一句描述

### 1.3 领域数据（中间结果）

| 字段 | 类型 | 写入者 | 读取者 | 说明 |
|------|------|--------|--------|------|
| `market_state` | dict | Market Agent (或 quant.market_regime) | Analyst Agent, 报告 Skill, 前端 | `{regime, style_bias, risk_level, summary, confidence}` |
| `universe_snapshot` | list[dict] | Data Skill (data.fetch_universe) | Quant Skill (筛选, 排名) | 全市场快照，约 30 字段。**通过 LangGraph `transient` reducer 标记为不参与 checkpoint 序列化**（2026-06-07 补强 P0-3）。**Skill 完成后写入 `skill_executions.output_result` 的摘要数据**（每只股票关键因子值），供恢复时重建轻量快照。 |
| `candidate_pool` | list[str] | Quant Skill (筛选) | Analyst Agent, 报告 Skill | 通过筛选的股票代码列表 |
| `analysis_results` | dict[str, AnalysisResult] | Analyst Agent (批量) | 汇总节点, 报告 Skill | key = stock_code，值为深度分析结果 |
| `report_content` | dict | 报告 Skill | 邮件 Skill, 前端 | `{markdown, html, pdf_path}` |
| `reflection_result` | dict | Reflection Agent | 汇总节点, 前端 | `{accuracy, avg_return, failed_cases, suggestions}` |

**AnalysisResult 结构**:
- `stock_code`, `stock_name`
- `total_score`: float
- `factor_scores`: dict
- `master_scores`: dict
- `debate`: `{bull_thesis, bear_thesis, verdict, confidence}`
- `recommendation`: `"strong_buy"` | `"buy"` | `"hold"` | `"sell"` | `"strong_sell"`
- `reasoning`: str

### 1.4 中断与恢复

| 字段 | 类型 | 写入者 | 读取者 | 说明 |
|------|------|--------|--------|------|
| `interrupt_data` | dict \| None | Interrupt 节点（中断时设置） | 前端（SSE 推送） | 中断时推送给用户的确认信息。结构见 M3.5-interrupt-mechanism.md §6 |
| `user_confirmation` | dict \| None | Interrupt 节点（恢复时注入） | execution_loop 后续节点 | 用户确认结果：`{action: "confirm"|"cancel"|"modify"|"timeout", params?: dict}` |
| `interrupt_consumed` | bool | Interrupt 节点（消费后设 True） | Interrupt 节点（幂等检查） | 防止重入，初始 False。恢复后设为 True |

**中断字段生产者/消费者关系**：

```
interrupt_node 执行:
  1. interrupt_data  ← 写入（推送给前端）
  2. interrupt() 暂停
  3. user_confirmation ← 恢复时注入（从前端 POST /confirm 来）
  4. interrupt_consumed = True ← 写入（标记已消费）
```

### 1.5 控制与配置

| 字段 | 类型 | 写入者 | 读取者 | 说明 |
|------|------|--------|--------|------|
| `config` | dict | 任务创建时注入 | 各节点 | 本次运行参数: `{date, style, portfolio_type, skip_email}` |

### 1.5 可观测性

| 字段 | 类型 | 写入者 | 读取者 | 说明 |
|------|------|--------|--------|------|
| `trace_log` | list[TraceEntry] | 执行调度器（自动） | 调试, 前端 | 步骤执行轨迹，含时间戳、耗时、成功/失败，不参与业务逻辑 |

## 2. State 的生命周期与持久化

**初始化**: 创建任务时生成 `run_id`，设置 `config` 和初始 `status='planning'`，注入用户消息到 `messages[0]`。其余字段为空。

**Checkpoint**: LangGraph 在每节点执行后自动保存 State。`universe_snapshot` 通过序列化过滤排除，因为它数据量大且只在一个步骤内使用。

#### §2.1 Checkpoint 持久化方案（2026-06-07 修订：用 AsyncSqliteSaver）

**核心结论**：**AsyncSqliteSaver 单文件，路径 `data/langgraph_checkpoints.db`**，与 M1 §1.4 主业务库 `data/agent.db` **分文件隔离**（避免表名空间冲突、WAL 文件竞争）。

> **为什么 AsyncSqliteSaver 而非 SqliteSaver**（2026-06-07 决议 P0-2）：FastAPI 是 async 运行时，`graph.astream()` 绑定到同步 `SqliteSaver` 虽不会阻塞事件循环（内部线程池包装），但产生不必要的线程切换开销。LangGraph 0.1+ 提供了 `AsyncSqliteSaver`，基于 `aiosqlite`，与 `astream` 原生兼容。如果当前环境版本 < 0.1，需升级；所有 LangGraph 操作（`astream`, `ainvoke`）统一走 async 路径。

**初始化代码（FastAPI 启动时，lifespan 内）**：
```python
# backend/server.py
from langgraph.checkpoint.sqlite.aio import AsyncSqliteSaver
from pathlib import Path

DATA_DIR = Path("data")
DATA_DIR.mkdir(exist_ok=True)
CHECKPOINT_DB = DATA_DIR / "langgraph_checkpoints.db"

# 启动时初始化，进程内单例（await 获取实例）
async with AsyncSqliteSaver.from_conn_string(
    f"sqlite+aiosqlite:///{CHECKPOINT_DB}",
    serde=JsonPlusSerializer(),
) as checkpointer:
    app.state.checkpointer = checkpointer
```

**图绑定（每次 `graph.astream` / `graph.ainvoke`）**：
```python
config = {
    "configurable": {
        "thread_id": run_id,         # LangGraph 强制要求，作为 checkpoint 主键
    },
    "checkpointer": app.state.checkpointer,    # 全进程共享
}
async for event in graph.astream(initial_state, config=config):
    # 处理事件流
    ...
```

**MemorySaver 切换条件（仅 dev 模式）**：
- `config.dev_mode_inmemory=True` → 用 `MemorySaver()` 替代 AsyncSqliteSaver（重启后所有 `waiting_user` 任务全丢，仅供快速调试）
- 生产/默认必须 AsyncSqliteSaver，**否则服务重启会破坏 Human-in-the-loop 流程**

**与 M1 SQLite 共存**：
- 文件隔离：`agent.db`（业务）+ `langgraph_checkpoints.db`（LangGraph）
- 进程内连接池**不共享**：业务库走 `shared.db_session`（M1 已有），LangGraph 走 AsyncSqliteSaver 独立连接
- 数据库连接字符串：业务库用 `sqlite:///data/agent.db`，LangGraph 用 `sqlite+aiosqlite:///data/langgraph_checkpoints.db`
- 备份策略：业务库每日 dump，checkpoint 库**保留 7 天后自动清理**（定时任务）

**生产部署硬要求**：
- ❌ 不要自己手写 checkpoint 存储（LangGraph 内部含 `_types.SchemaMeta._types.Channel` 等对象，序列化必须用 LangGraph 自家的 `JsonPlusSerializer`）
- ❌ 不要把 checkpoint 与业务库合表（LangGraph 表 schema 不稳定，未来 LangGraph 升级会破坏业务表）

→ 由 software-product-manager 于 2026-06-07 补强，依据 review 第 2 轮 P0-1。

#### §2.2 Checkpoint 双段保留（2026-06-07 补强 P0-2）

**原设计冲突**：M3.5 §7 提到"7 天保留"，M4 §7 提到"1 小时保留"——两处不一致。

**解决（双段保留）**：

| 段 | 时长 | 机制 | 用途 |
|----|------|------|------|
| **热保留** | 1 小时 | LangGraph `SqliteSaver` 原生 checkpoint | 用户中断后 1 小时内可快速 `Command(resume=...)` 恢复执行 |
| **冷保留** | 7 天 | 数据库 `agent_runs.plan_json` + `skill_executions.output_result` + `conversation_history.messages_json` | 超过 1h 但 7d 内：用户可查看 run 历史、调试复盘；**不可恢复执行**，如需重跑则发起新 run_id |

**`agent_runs.checkpoint_retention_hours` 字段**（M1 §1.5 新增）：
- 默认值 24（可在 config.yaml 调整）
- 控制**冷保留清理时间**——每日 04:00 扫描任务删除 `created_at < now() - retention_hours` 的 `agent_runs` 记录（详见 M1 §1.10.1）。
- **不控制 LangGraph SqliteSaver 的清理**——LangGraph 内部 checkpoint 由 LangGraph 自身策略（默认 7d）管理，每日定时 `DELETE FROM checkpoints WHERE thread_id NOT IN (SELECT run_id FROM agent_runs WHERE created_at > now() - 7d)`。

**前端感知**：
- 用户中断后 1 小时内：前端"恢复"按钮可用，调用 `POST /api/tasks/{run_id}/confirm` 走 LangGraph 恢复路径。
- 超过 1h 但 7d 内：前端"恢复"按钮 disabled，hover 提示"超过 1 小时不可恢复，可查看历史"，改用 `GET /api/tasks/{run_id}/status`（F-13 新增端点）查询。
- 超过 7d：记录已从数据库删除，API 返回 404。

→ 由 software-product-manager 于 2026-06-07 补强，依据 P0-2 解决方案。

#### §2.3 `universe_snapshot` 排除机制实现（2026-06-07 修订 P0-3：自定义 reducer + SkillExecutor 内存桥）

> **2026-06-07 重要修订**：LangGraph 0.0.40+ 的 `Annotated` 没有内置 `transient` reducer。替代方案为**自定义 reducer `_drop_universe`** + **SkillExecutor 内存桥**。

**实现方案**（两路并行）：

**A 路 — State 层面：自定义 reducer 丢弃**
```python
from typing import Annotated

def _drop_universe(current: list | None, update: list | None) -> None:
    """无论如何都丢弃 universe_snapshot，不让它进入 checkpoint。
    
    - 不返回 update（= 丢弃传入值）
    - 不抛出异常（区别于 REJECT）
    - 节点内通过 SkillExecutor 内存桥获取 snapshot
    """
    return None   # 永远不写入 state

class AgentState(MessagesState):
    universe_snapshot: Annotated[list, _drop_universe]
    ...
```

**B 路 — 运行时：SkillExecutor 内存桥**
- `SkillExecutor` 实例维护 `self._last_universe_snapshot: dict | None` 实例变量。
- Data Skill `data.fetch_universe_snapshot` 执行后，结果同时存入 `self._last_universe_snapshot`。
- 后续 Quant Skill 通过 `SkillExecutor.get_last_snapshot()` 获取，**不走 State**。
- 内存桥的生命周期绑定 FastAPI request 级别（同一 run 内有效），不会跨请求泄漏。

**轻量摘要持久化（兜底）**：
- 包含 `universe_snapshot` 的 Skill 执行完成后，同时写入 `skill_executions.output_result` 的精简摘要（`{stock_code: {factor1, factor2, ...}}`，~500KB）。
- 中断恢复后，执行引擎检测到 `state["universe_snapshot"] is None`：
  1. 查 `skill_executions` 中该 step 的 `output_result` 是否有摘要 → 重建轻量快照
  2. 若无（首次中断在 fetch 途中）→ **自动补调一次 `data.fetch_universe_snapshot`**（通过 `idempotency_key` 命中缓存，不重复拉取）

→ 由 software-product-manager 于 2026-06-07 修订，依据 P0-3 决议：`transient` 不存在，改用 `_drop_universe` reducer + SkillExecutor 内存桥。

**SSE 推送**: 前端不需要完整 State，只从 State 提取视图模型：`status`、`current_step_index`、`execution_plan`（进度）、新增 `messages` 片段、`market_state` 等卡片数据、`interrupt_data`（需确认时）。

## 3. 关键字段读写约束

| 约束 | 说明 |
|------|------|
| `messages` 只追加 | 仅 Master Agent 在"生成回复"时追加 assistant 消息；用户消息由 API 层注入；**Interrupt 节点在暂停和恢复时各追加一条 system 消息**（2026-06-07 补强 P0-4 / F-5）。保证对话历史线性、可审计。 |
| `execution_plan` 执行期不可修改 | Master Agent 生成后锁定。失败重规划时整体替换并重置 `current_step_index`。 |
| `step_results` 按 step_id 隔离 | 步骤间通过 `"$step_id.field"` 占位符变量替换解耦。 |

### §3.1 system 消息注入时机（2026-06-07 补强 F-5）

**注入点清单**：

| 节点 | 时机 | system 消息内容 |
|------|------|-----------------|
| `init` | 任务创建时 | "今天是 {date}，用户风格偏好 {style}，市场风险等级 {risk_level}。" |
| `interrupt_node` 暂停时 | 调用 `interrupt()` 前 | "系统提示：已向用户请求确认（类型：{type}）。等待用户操作…" |
| `interrupt_node` 恢复时 | 处理 `user_confirmation` 后 | "用户已执行：{action}。{action == 'modify' ? '用户修改参数：' + params : ''}" |
| `error_handler` | 终态写入时 | "任务已终止，状态：{status}，原因：{status_reason}" |

**持久化**：所有 messages 通过 **`asyncio.create_task(write_conversation_history(run_id, messages))` 异步写入** `conversation_history.messages_json`，不阻塞图执行。写入时点：
- `init` 节点：写入用户第一条消息
- `interrupt_node`：写入 system 消息（中断提示）
- `summarize` 节点：写入最终 assistant 回复
查询历史时从 `conversation_history` 表读取（`WHERE run_id = ? ORDER BY id`），不分页（单次任务 50 条以内）。清理策略随 `agent_runs` 同步（7 天后清理）。

### §3.2 `interrupt_consumed` 字段（与 M3.5-interrupt-mechanism §8.1 协作）

**新增字段**：`interrupt_consumed: bool`，写入者/读取者均为 `interrupt_node` 函数（见 M3.5 §8.1）。

## 4. 设计取舍记录

| 决策 | 理由 |
|------|------|
| 扁平 State，不嵌套 | 嵌套增加序列化复杂度和节点耦合；通过 `step_results` + 变量替换实现依赖 |
| `universe_snapshot` 不持久化到 checkpoint | 数据量大，仅单步骤使用，checkpoint 只需记录"已完成" |
| `status` 增加 `waiting_user` | 区别于 `executing`，前端据此显示确认界面 |
| `status` 增加 `cancelling` 中间态 | 用户在 SSE 流关闭时点击"停止"需要 `cancelling` → `cancelled` 两步走，避免 state 跳变（详见 §4.1 状态机时序） |
| `trace_log` 与 `step_results` 分离 | 前者是观测数据，后者是业务数据，混在一起污染业务逻辑 |

#### §4.1 "modify" 语义说明（Product Decision）

**MVP 阶段决策**：`modify` 操作 **= `confirm` + 重新 init**，等价于"整图重跑"。

**行为定义**：
- 用户在 confirm 卡片选择"修改参数"（如"换成中庸风格"、"候选池 20 只"）→ 前端 `POST /api/tasks/{run_id}/confirm`，body 携带 `action: "modify", params: {style: "neutral", max_candidates: 20}`。
- 后端接收后：
  1. **不销毁旧 checkpoint**——旧 checkpoint 自然过期（24 小时热保留后 LangGraph 自动清理）。
  2. **生成新 run_id**（UUID4），将 `agent_runs` 表的 `parent_run_id` 指向旧 run_id。
  3. 旧 `agent_runs` 记录 `status = "cancelled"`，`status_reason = "用户修改参数后重新发起"`。
  4. **新任务从 `plan_generator` 重新开始**（使用修改后的 `config`），生成新 ExecutionPlan，写入新 `agent_runs` 记录。
  5. 返回**新 SSE 流**（新 run_id 的 event stream），前端旧 EventSource 收到 `task_complete(status=cancelled)` 后自然关闭。
  6. 前端切换到新 run_id，建立新 EventSource。

> **为什么不是"销毁旧 checkpoint"**（2026-06-07 修正 P0-3）：销毁后 LLM 将无法回溯修改前上下文，且存在 SQLite 并发删除风险。新 run_id + parent_run_id 关联更安全可审计，检查点自然过期无需主动干预。

**明确禁止**："局部重跑"——即"只重跑受影响的 step 而跳过已完成的"——**MVP 阶段不支持**。理由：
- 状态依赖复杂，错误风险高
- 局部重跑结果与全图重跑结果可能不一致，调试困难

### 附录 A：状态机汇总（整合自 STATE-MACHINE.md）

**AgentRun.status 全部合法转换**：

```
pending → planning → executing → waiting_user → executing (用户确认)
                                         → cancelling → cancelled (取消/超时)
              → completed / failed (终态)
```

**完整转换图（含触发条件）**：

```
┌──────────┐   init 完成     ┌──────────┐  plan 生成    ┌───────────┐
│ pending  │ ──────────────→ │ planning │ ───────────→  │ executing │
└──────────┘                  └──────────┘               └─────┬─────┘
                                                                  │
                                    ┌─────────────────────────────┼─────────────────────────────┐
                                    │                             │                             │
                                    ▼                             ▼                             ▼
                           ┌──────────────┐              ┌──────────────┐             ┌──────────────┐
                           │ waiting_user │              │  completed   │             │   failed     │
                           └──────┬───────┘              └──────────────┘             └──────────────┘
                              │     │                                                    ↑      ↑
                    用户确认   │     │ 取消/超时                                          │      │
                              ▼     ▼                                                    │      │
                       ┌──────────┐                                                   (详见下) (详见下)
                       │ executing │
                       └──────────┘
                              │
                              │ 用户取消 / 30min 超时
                              ▼
                       ┌─────────────┐  清理完成   ┌───────────┐

                       └─────────────┘            └───────────┘
```

#### §A.1 `executing → failed` 触发条件（任一满足即触发）

| # | 触发条件 | `status_reason` 值 | 触发位置 | 可恢复？ |
|---|---------|-------------------|----------|---------|
| 1 | **节点抛不可恢复异常**（非 `AShareXError` 子类或 `AShareXError.recoverable=False`） | `{ExceptionName}: {str(e)[:200]}` | 当前节点 → error_handler | 否 |
| 2 | **`node_count >= 200`**（主图 execution_loop 硬限） | `"node_count_exceeded"` | execution_loop 自检 | 否 |
| 3 | **LLM 调用失败且重试耗尽**（`intent_parser` / `plan_generator` / `summarize` 节点，默认重试 1 次） | `"llm_call_failed: {model_name}"` | 对应 LLM 节点 | 部分可恢复（换模型后可重试） |
| 4 | **SkillExecutor 全部重试耗尽**（`max_retries` 次数用尽仍抛异常，且该步骤无 fallback Skill） | `"skill_exhausted: {skill_name}"` | skill_executor_node | 步骤级可跳过（见 M3 §3.8 降级策略） |
| 5 | **plan_validator 校验失败**（生成的 ExecutionPlan 含未注册 target、循环依赖等） | `"plan_validation_failed: {reason}"` | plan_generator 后置校验 | 是（重新生成计划） |
| 6 | **初始化失败**（init 节点无法构造初始 State，如 config 缺失必填项） | `"init_failed: {reason}"` | init_node | 否 |

> **注意**：单个 Skill/Agent 步骤失败**不直接导致 `failed`**——错误被捕获追加到 `state["errors"]`，执行继续。只有上述 6 种"全局性失败"才终止整个 run。

> **与 `errors` 字段的关系**：`failed` 终态时 `state["errors"]` 包含所有已记录的错误条目；`status_reason` 记录的是**导致终态的直接原因**（最后稻草），不是全部错误历史。

#### §A.2 `cancelling` 清理行为清单

当用户点击"停止"或 30 分钟超时时，状态进入 `cancelling`。清理协程按以下顺序执行：

| 步骤 | 操作 | 超时 | 失败处理 |
|------|------|------|---------|
| 1 | 向 LangGraph 图发送取消信号（`graph.acancel()` 或设置内部 cancel token） | 5s | 强制跳过，记 WARNING 日志 |
| 2 | 关闭正在进行的 LLM 流式连接（如 summarize 正在流式输出） | 3s | 直接关闭 HTTP 连接 |
| 3 | 中止正在执行的同步 Skill（通过 `ThreadPoolExecutor.shutdown(wait=False, cancel_futures=True)` 提交的 future） | 5s | 标记为 abandoned，不等待 |
| 4 | 将已完成的 `step_results` 写入 `agent_runs.plan_json` 的 partial 快照 | 2s | 异步 fire-and-forget |
| 5 | 更新 `agent_runs.status = "cancelled"`，写入 `status_reason = "user_cancel"` 或 `"timeout_30m"` | — | 必须成功，否则 DB 不一致 |
| 6 | 追加 system 消息到 `messages`："任务已取消，原因：{status_reason}" | — | 同步写 conversation_history 表 |

**清理完成后**：`status` 从 `cancelling` → `cancelled`（终态）。SSE 推送最终 `task_complete(status="cancelled")`。

**前端感知**：
- `cancelling` 持续时间通常 < 15s（大部分是等 LLM/Skill 超时）
- 若清理超过 30s 未完成，强制进入 `cancelled`（硬超时兜底）

**禁止在清理期间的操作**：
- ❌ 不能接受新的 `/confirm` 请求（返回 400 `"任务正在取消中"`）
- ❌ 不能启动新的 Skill 执行
- ❌ 不能修改 `execution_plan`

### 附录 C：plan_validator 重试策略（P1-Q4.1 补强，2026-06-07）

**背景**：M3 §3.3 提到"校验失败时返回错误并请求重新规划"，但**重试次数、是否计入 node_count、最终失败时的状态转换**未明确。本附录补全。

**plan_validator 失败分类**：

| 错误码 | 原因 | 是否重试 |
|--------|------|---------|
| `UNKNOWN_TARGET` | `step.target` 不在 `skill_registry` 已注册列表 | 否（结构性错误，重试也是同样的 target） |
| `CIRCULAR_DEPENDS` | `depends_on` 形成环 | 否（同上） |
| `MISSING_DEPENDS` | `depends_on` 引用不存在的 `step_id` | 否 |
| `INVALID_TYPE` | `step.type` 不在 5 个枚举值内 | 否 |
| `CONFIRM_PLACEMENT` | `confirm_*` 步骤位置不当（如在最后一步） | 否（结构性问题） |
| `LLM_HALLUCINATION` | LLM 生成了语法/语义上不通过 schema 的计划 | ✅ 是 |
| `SCHEMA_PARSE_ERROR` | `with_structured_output` 解析失败 | ✅ 是 |

**重试策略**：

```python
class PlanValidator:
    MAX_RETRIES = 1  # plan_generator 节点内最多重试 1 次
    RETRY_BACKOFF_SECONDS = 0  # 立即重试（不引入延迟）
    
    def validate(self, plan: ExecutionPlan) -> ValidationResult:
        """校验计划，返回结果 + 错误列表。"""
        errors = []
        for step in plan.steps:
            if step.target not in self.registry and step.type in ("skill", "agent"):
                errors.append(ValidationError("UNKNOWN_TARGET", f"step_id={step.step_id} target={step.target}"))
            # ... 其他校验
        
        if errors:
            return ValidationResult(valid=False, errors=errors)
        # 检测环
        if self._has_circular_dep(plan):
            return ValidationResult(valid=False, errors=[ValidationError("CIRCULAR_DEPENDS", "...")])
        return ValidationResult(valid=True)
```

**plan_generator 节点内的重试流程**：

```
1. LLM 生成计划（with_structured_output）
2. 调用 plan_validator.validate(plan)
3. 若 valid=True → 写入 state.execution_plan，继续
4. 若 valid=False 且错误均为"可重试"类（LLM_HALLUCINATION / SCHEMA_PARSE_ERROR）且重试次数 < 1：
   a. 重新调用 LLM，prompt 中追加错误信息：
      "上次的计划有如下错误：{errors}。请重新生成符合要求的计划。"
   b. 重试次数 + 1，回到步骤 2
5. 若 valid=False 且重试次数用尽 或 错误为"不可重试"类：
   → 抛 AShareXError(recoverable=False, reason="plan_validation_failed")
   → 走 error_handler 节点
   → status="failed", status_reason="plan_validation_failed: {first_error_message}"
   → node_count 计入 +1（plan_generator 节点本身）
```

**node_count 计入**：
- plan_generator 节点重试时，**每次进入都递增 1**（含重试）
- 如果连续 3 次进 plan_generator（含重试 1 次 + 外部 retry 机制），node_count = 3
- 在 200 硬限下，3 次占据 1.5% 配额，可接受

**用户感知**：
- 重试时 SSE 推送 `status_change(status="planning")` 多次（前端可看到"重新规划中…"）
- 重试耗尽失败时推送 `task_complete(status="failed", status_reason="plan_validation_failed: UNKNOWN_TARGET step_id=s5")`
- 前端错误卡显示具体错误原因，方便用户反馈

**为什么 MAX_RETRIES=1 而非更多**：
- LLM 在 1 次错误反馈后通常能修正（如纠正 target 名称）
- 超过 1 次的重试通常是结构性错误，再试也无效
- 重试占用 node_count 配额

### 附录 D：`$ref` 占位符实现规范（P1-Q4.3 补强，2026-06-07）

**背景**：M3.5 §3 提到 `step.params` 支持 `"$step_id.field"` 占位符，但**Pydantic schema 约束、错误处理、嵌套访问**未定义。本附录补全。

**支持的占位符语法**：

| 语法 | 含义 | 示例 |
|------|------|------|
| `"$step_id"` | 引用整个 step_results[step_id] | `"params": {"prev": "$s3"}` |
| `"$step_id.field"` | 引用 step_results[step_id]["field"] | `"params": {"market_state": "$s4.data"}` |
| `"$step_id.field.nested"` | 多层嵌套访问 | `"params": {"code": "$s5.candidate_pool[0]"}` |
| `"$step_id.list[*].field"` | 列表展开（**Phase 2+**） | `"params": {"stocks": "$s5.candidate_pool[*]"}` |

**MVP 阶段仅支持前 3 种**，`[*]` 语法 Phase 2+。

**Pydantic schema 约束**（在 `shared/schemas.py`）：

```python
class PlanStep(BaseModel):
    step_id: str = Field(..., regex=r"^s\d+$|^c\d+$")  # 约束命名
    type: Literal["skill", "agent", "confirm_plan", "confirm_email", "wait_for_user"]
    target: str | None = None
    params: dict  # 内部值可以是 $ref 字符串
    depends_on: list[str] = []
    description: str | None = None
    
    @field_validator("params")
    @classmethod
    def validate_refs(cls, v: dict) -> dict:
        """检查所有 string 值是否是合法 $ref 语法（不实际解析，只检查格式）"""
        import re
        REF_PATTERN = re.compile(r"^\$[a-zA-Z0-9_]+(\.[a-zA-Z0-9_]+|\[\d+\])*$")
        for key, val in v.items():
            if isinstance(val, str) and val.startswith("$"):
                if not REF_PATTERN.match(val):
                    raise ValueError(f"Invalid $ref syntax in params.{key}: {val}")
        return v
```

**`_resolve_vars` 函数实现**（在 `backend/agent/utils.py`）：

```python
def _resolve_vars(params: dict, step_results: dict) -> dict:
    """递归解析 params 中的 $ref 占位符。
    
    错误处理：
    - $ref 引用不存在的 step_id → 抛 AShareXError("UNKNOWN_REF", step_id, ref)
    - $ref 引用的字段不存在 → 抛 AShareXError("MISSING_FIELD", ref)
    - $ref 引用类型不匹配（如 step 还在 running）→ 抛 AShareXError("REF_NOT_READY", ref)
    """
    resolved = {}
    for key, val in params.items():
        resolved[key] = _resolve_value(val, step_results)
    return resolved


def _resolve_value(val, step_results):
    if isinstance(val, str) and val.startswith("$"):
        # 解析 $ref
        parts = val[1:].split(".")
        step_id = parts[0]
        if step_id not in step_results:
            raise AShareXError(f"UNKNOWN_REF: {val}", detail={"ref": val, "step_id": step_id})
        result = step_results[step_id]
        for part in parts[1:]:
            # 处理 list[index]
            if "[" in part and part.endswith("]"):
                field, idx = part[:-1].split("[")
                if field:
                    result = result[field]
                result = result[int(idx)]
            else:
                if part not in result:
                    raise AShareXError(f"MISSING_FIELD: {val}", detail={"ref": val, "field": part})
                result = result[part]
        return result
    elif isinstance(val, dict):
        return {k: _resolve_value(v, step_results) for k, v in val.items()}
    elif isinstance(val, list):
        return [_resolve_value(item, step_results) for item in val]
    else:
        return val
```

**`depends_on` 校验**：

`_resolve_vars` 是在节点内**运行时**调用，校验 step 间依赖在 **`plan_validator` 静态校验**时做：

```python
def _validate_depends_on(plan: ExecutionPlan) -> list[ValidationError]:
    """校验所有 depends_on 引用了已定义的 step_id（不验证结果是否就绪，那是运行时的事）"""
    errors = []
    defined_steps = {step.step_id for step in plan.steps}
    for step in plan.steps:
        for dep in step.depends_on:
            if dep not in defined_steps:
                errors.append(ValidationError("MISSING_DEPENDS", f"step_id={step.step_id} depends_on={dep} not defined"))
    return errors
```

**错误传播**：

- `UNKNOWN_REF` / `MISSING_FIELD` → 节点抛 `AShareXError(recoverable=False)` → 走 error_handler
- 状态：`status="failed"`, `status_reason="ref_error: UNKNOWN_REF $s5.field"`
- **不算 LLM 错误，是计划结构错误**，应该让用户看到具体哪个引用出问题

**示例**：

```json
{
  "step_id": "s7",
  "type": "skill",
  "target": "report.generate_markdown",
  "params": {
    "recommendations": "$s6.analysis_results",
    "market_state": "$s4.data",
    "date": "2026-06-07"
  },
  "depends_on": ["s4", "s6"]
}
```

`skill_executor_node` 内：
```python

# params = {
#   "recommendations": {"600519": {...}, "000858": {...}, ...},

```

### 附录 E：`errors` 字段上限策略（P1-Q3.3 补强，2026-06-07）

**背景**：M3.5 §1.2 定义 `errors: list[ErrorEntry]`，但**无长度上限**。20 只股票 × 5 个 tool call × 1 错误 = 100 条，全部序列化到 checkpoint 会拖慢持久化。

**上限与保留策略**：

| 维度 | 限制 | 实现 |
|------|------|------|
| `errors` 列表最大长度 | 50 条 | append 超 50 时 pop oldest |
| 单条 error 长度 | `message + detail` 序列化后 ≤ 2KB | 序列化超 2KB 时截断并追加 `truncated=True` 标记 |
| 序列化到 checkpoint | 同上 | LangGraph JsonPlusSerializer 自动处理 |
| 终态 `status="failed"` 时 | 全量保留（不再 LRU 淘汰） | `error_handler` 节点不再触发 pop |

**实现**（在 `backend/agent/utils.py`）：

```python
from collections import deque

ERROR_LIST_MAX = 50
ERROR_ENTRY_MAX_BYTES = 2048


def append_error(errors: list, new_error: ErrorEntry, is_terminal: bool = False) -> list:
    """追加错误，超出上限时 LRU 淘汰。
    
    - is_terminal=True: 终态时不再淘汰，全量保留
    - 单条超过 2KB 时截断
    """
    if len(new_error.message) + len(json.dumps(new_error.detail)) > ERROR_ENTRY_MAX_BYTES:
        new_error = new_error.copy(truncated=True, message=new_error.message[:200] + "...")
    
    if is_terminal:
        return errors + [new_error]  # 终态全量保留
    
    if len(errors) >= ERROR_LIST_MAX:
        return errors[1:] + [new_error]  # 淘汰最早一条
    return errors + [new_error]
```

**前端展示策略**：

- 任务进行中：`chatStore.errors` 显示最近 5 条
- 任务终态（failed）：显示全部 50 条
- 超 50 条时：`+ N more errors` 折叠面板

**与 `errors` 字段的关系**（M3.5 §A.1）：`failed` 终态时 `state["errors"]` 包含所有已记录的错误条目；`status_reason` 记录的是**导致终态的直接原因**（最后稻草），不是全部错误历史。本附录新增的"终态全量保留"是为了让用户能看到完整错误链路（不只是 `status_reason` 那一条）。

**下一节**: [Interrupt 机制设计](M3.5-interrupt-mechanism.md)
